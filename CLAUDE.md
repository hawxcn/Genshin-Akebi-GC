## Overview

Akebi-GC is a Windows-only C++ game modification for Genshin Impact. It is a DLL (`CLibrary.dll`) that hooks into the game's IL2CPP runtime, plus a separate `injector.exe` that launches the game suspended and injects the DLL. All features render through an ImGui overlay (F1 opens the GUI in-game).

## Building

- **Toolchain:** Visual Studio 2022 (v17), MSBuild, Windows target only. Build from the solution `akebi-gc.sln`.
- **Clone with submodules** — the entire `cheat-base/vendor/*` tree (imgui, fmt, json, detours, etc.) lives in git submodules:
  ```
  git submodule update --init --recursive
  ```
- **CI build command** (see `.github/workflows/main.yml`):
  ```
  msbuild /m /p:Configuration=Release akebi-gc.sln
  ```
- **Platform:** Always x64. The solution maps all x86 configurations to x64 under the hood — there is no real 32-bit build.
- **Output:** `bin/<Configuration>-x64/` (e.g. `bin/Release-x64/`). `CLibrary.dll` and `injector.exe` must sit in the same folder to run.

### Build configurations

- `Debug` / `Release` — normal builds. Use static IL2CPP offsets from `src/appdata/`.
- `Release_WithScanner` (project config `Release_WS`) — defines `_PATTERN_SCANNER`, enabling runtime pattern scanning to recover offsets when the static ones don't match the current game version.
- **Custom build steps auto-launch the game+injector after building** (a `PostBuildEvent`/custom command runs `injector.exe` then sleeps). CI disables this with a `CustomBuildStepsDisabler` tool. When building locally and you do *not* want the game to launch, disable the custom build step on the `cheat-library` project.

There is no test suite, linter, or automated test runner in this repo.

## Architecture

Three projects (dependency order):

1. **`cheat-base`** — engine-agnostic framework. No knowledge of Genshin. Provides: the `Feature` base class and `CheatManagerBase`, config/serialization system (`config::Field`), event system (`TEvent`), hooking (`HookManager` over Microsoft Detours), pattern scanning, ImGui rendering backend (D3D11), logging, and DLL injection (`inject/`). Bundles all third-party vendor libs.
2. **`cheat-library`** — the actual cheat DLL (`CLibrary.dll`). Contains Genshin-specific IL2CPP bindings and all game features. Depends on `cheat-base`.
3. **`injector`** — standalone `injector.exe`. Launches Genshin suspended (reparented under `explorer.exe`), injects the DLL, then resumes. Reads paths from `cfg.ini`.

### DLL entry & init flow

`cheat-library/src/framework/dllmain.cpp` → `Run()` in `src/user/main.cpp`:
1. Load config (`cfg.json`), set up logging.
2. `DebuggerBypassPre()`, wait for `UserAssembly.dll`, sleep for game init, `DebuggerBypassPost()`.
3. `init_il2cpp()` — resolves all game function/type addresses (see below).
4. `cheat::Init()` (`src/user/cheat/cheat.cpp`) — registers every feature and installs global hooks.

### IL2CPP binding layer (`src/appdata/`, `src/framework/il2cpp-init.cpp`)

These files are **generated by Il2CppInspector** from the game binary — treat them as generated code, not hand-authored. They declare thousands of `app::*` function pointers, types, and offsets via `DO_API` / `DO_APP_FUNC` / `DO_TYPEDEF` X-macros.

`init_il2cpp()` resolves addresses one of two ways:
- **Static offsets** (`init_static_offsets`) — base address + hardcoded offset. Used when `IsStaticCheckSumValid()` confirms the game binary matches the shipped `assembly_checksum.json`.
- **Pattern scanning** (`init_scanned_offsets`, only compiled with `_PATTERN_SCANNER`) — searches signatures from `res/signatures.json` to recover offsets after a game update, caching results in `cfg.json`. This is what lets the cheat survive minor game patches.

### Feature system

Every feature is a singleton subclass of `cheat::Feature` (`cheat-base/.../cheat/Feature.h`). Pattern (see `src/user/cheat/player/GodMode.cpp` as the canonical example):

- Private constructor installs the feature's game hooks via `HookManager::install(app::SomeGameFunc, MyHook)`.
- `GetInstance()` returns the static singleton.
- Config fields declared as `config::Field<...>` and initialized in the constructor with the `NFEX`/`NF`/`NFS` macros (defined in `config/Config.h`). These auto-persist to `cfg.json` and auto-generate GUI widgets. `NFS`/`shared=true` fields are shared across profiles.
- `GetGUIInfo()` returns `{ name, moduleName, isGroup }` — `moduleName` ("Player", "World", "Visuals", etc.) determines which GUI tab the feature lands in.
- `DrawMain()` renders the feature's controls (usually via `ConfigWidget(...)`). Optional `DrawStatus()`/`DrawInfo()` render the on-screen status/info overlays.

**To add a feature:** create the class under the appropriate `src/user/cheat/<module>/` folder, then register it in the `manager.AddFeatures({...})` list in `cheat.cpp`. Tab ordering is set by `manager.SetModuleOrder({...})` in the same file.

Feature module folders: `player/`, `world/`, `teleport/`, `visuals/`, `esp/`, `imap/` (interactive map), `misc/` (settings, hotkeys, debug, about, packet sniffer), `game/` (shared game abstractions like `EntityManager`).

### Hooking conventions

- `HookManager::install(app::TargetFn, HookFn)` — detour a game function. Inside the hook, call the original with the `CALL_ORIGIN(HookFn, args...)` macro.
- Wrap hook bodies that touch game state in `SAFE_BEGIN()` / `SAFE_EEND()` (SEH guard) to avoid crashing the game on bad reads.
- `GET_SINGLETON(TypeName)` fetches a game singleton instance; guard for `nullptr`.
- `UPDATE_DELAY(ms)` throttles per-frame update logic.
- Global per-frame logic hangs off `events::GameUpdateEvent` (fired from the `GameManager::Update` hook in `cheat.cpp`). Other cross-feature signals: `AccountChangedEvent`, `MoveSyncEvent`.

### Resources (`cheat-library/res/`)

Compiled into the DLL via `res.rc`. Includes the ImGui font, map data JSON (`map_*.json`), icon sets (`icons/`, `iconsHD/`), IL2CPP `signatures.json`, and `assembly_checksum.json`. Helper Python scripts in `res/scripts/` regenerate map/icon/offset data (not part of the build).
